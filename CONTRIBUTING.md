# Contributing to feaweld

Thanks for your interest in improving feaweld! This guide covers the
development setup and the project's conventions.

## Development setup

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"          # core + test dependencies
pip install -e ".[all]"          # everything (fenics, calculix, viz, ml, digital-twin)
pip install -e ".[docs]"         # documentation toolchain (mkdocs)
```

Optional system dependencies: [Gmsh](https://gmsh.info) ships as a Python
wheel; [FEniCSx](https://fenicsproject.org) and
[CalculiX](https://www.calculix.de) (`ccx` on PATH, or set `CCX_PATH`) enable
the FEA solve paths. Everything else works without them.

## Running tests

```bash
pytest tests/ -x -v                            # all tests
pytest tests/ -m "not requires_fenics and not requires_calculix"   # skip solver-bound tests
pytest tests/ -k "test_dong"                   # by name pattern
```

Markers: `requires_fenics`, `requires_calculix`, `requires_gmsh`, `slow`.
Tests are gated with `pytest.importorskip(...)` for optional dependencies —
follow that pattern so the suite passes on minimal installs.

Shared fixtures live in `tests/conftest.py` (`simple_plate_mesh`,
`simple_3d_mesh`, `uniform_stress_results`, `gradient_stress_results`,
`sample_weld_line`, `FakeBackend`, ...). Reuse them rather than rebuilding
meshes inline.

## Code conventions

- **Docstrings: numpy style only.** `Parameters` / `Returns` sections with
  dashed underlines; no Google-style `Args:` blocks and no Sphinx roles
  (`:class:`, `:func:`, `:math:`). Cross-reference API objects with
  mkdocstrings syntax `[SNCurve][feaweld.core.types.SNCurve]` and write math
  as MathJax (`$\sigma_{hs}$`). Example:

  ```python
  def hotspot_stress(results, weld_line):
      """Compute hot-spot stress by surface extrapolation.

      Parameters
      ----------
      results : FEAResults
          Solved FE results with a stress field.
      weld_line : WeldLineDefinition
          Weld toe line to evaluate.

      Returns
      -------
      list[HotSpotResult]
          One entry per weld-toe node.
      """
  ```

- **Lazy imports for heavy optional deps.** matplotlib, pyvista, plotly,
  sklearn, emcee, websockets, and the solver backends must only be imported
  inside function bodies (see `visualization/plots_2d.py` for the pattern).
  `import feaweld` must succeed with only the core dependencies installed.
- **Solver-agnostic results.** Post-processors consume
  [FEAResults][feaweld.core.types.FEAResults] only — never call solver-backend
  methods from post-processing code.
- **Frozen data contracts.** Shared types in `core/types.py` are dataclasses /
  Pydantic models; add fields with backward-compatible defaults so existing
  YAML case files keep validating.
- No linter or formatter is configured; match the style of the surrounding
  code.

## Adding a post-processing method

The short version (the full walkthrough is in
[docs/tutorials/03_custom_postprocessing.md](docs/tutorials/03_custom_postprocessing.md)):

1. Add a standalone module under `src/feaweld/postprocess/` that consumes
   `FEAResults` and returns a small result dataclass.
2. Add an enum value to `StressMethod` in `core/types.py`.
3. Add a dispatch branch in `_run_postprocess()` in `pipeline/workflow.py`
   returning a dict (include `"max_stress"` and/or `"fatigue_life"` so the
   fatigue assessment picks it up).
4. Add tests under `tests/` using the conftest fixtures.
5. Document it: a section in the relevant guide plus the YAML field reference
   in tutorial 01.

## Documentation

```bash
mkdocs serve                          # live preview at http://127.0.0.1:8000
mkdocs build --strict                 # must pass with zero warnings
python scripts/generate_docs_images.py   # regenerate docs/images/*.svg
```

Diagrams in docs pages are Mermaid code blocks (rendered by mkdocs-material);
images embedded in `README.md` are static SVGs generated by the script above
so they render outside MkDocs too.

## Examples

Each example is a self-contained script under `examples/` with a module
docstring stating what it demonstrates and which extras it needs. If a feature
is YAML-reachable, prefer shipping a commented `.yaml` case next to the script
and listing both in `examples/README.md`.
